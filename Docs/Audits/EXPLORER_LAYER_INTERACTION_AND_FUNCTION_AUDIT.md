# ONHARU 2.0 레이어·입력 개선 및 기능 감사

> 이 문서는 공식 2.0이 개발 코드명 V3였던 시점의 감사 기록을 정리한 것이다.

작성일: 2026-08-14  
당시 범위: 개발 코드명 V3만 조사·수정. V1과 구형 V2 프로토타입, 사용자 데이터는 수정하지 않음.

## 1. 현재 구조

- **위치 조정 상태**: 원본 V1 WPF 창을 표시한다. 이동·크기 조절·클릭 감각은 V1 동작을 그대로 사용한다.
- **고정 상태**: WPF 화면을 32비트 BGRA 캐시로 만든 뒤 Explorer의 `SysListView32` `NM_CUSTOMDRAW / CDDS_PREPAINT` 단계에서 그린다. 따라서 배경화면보다 위, 바탕화면 아이콘보다 아래에 달력이 위치한다.
- **고정 상태 입력**: Explorer 훅이 좌표를 받으면 별도 action sink 창에 전달하고, 숨겨진 WPF 시각 트리에서 실제 컨트롤을 판정하여 V1 동작을 실행한다.

## 2. 문제가 있었던 방식과 해결

| 문제 | 원인 | 최종 해결 |
|---|---|---|
| WorkerW에 연결됐다고 나오지만 달력이 보이지 않음 | 창 계층 연결 성공과 DWM의 실제 합성 경로 참여는 별개 | WorkerW 경로를 버리고 `SysListView32`의 실제 페인트 파이프라인에 참여 |
| 달력이 아이콘을 덮거나 깜빡임 | 별도 창/사후 페인트가 Explorer 재그리기와 경쟁 | `CDDS_PREPAINT`에 캐시 프레임을 먼저 그리고, 그 위에 Explorer가 아이콘을 그림 |
| 과노출·색 손상 | 호환 비트맵 및 알파가 불명확한 픽셀 사용 | 32비트 BGRA 캐시와 확정된 불투명 알파 사용 |
| 고정 상태 클릭 위치가 어긋남 | 화면 DPI와 WPF 논리 좌표를 클릭 순간의 다른 기준으로 환산 | 프레임 생성 당시 DPI 변환을 저장·재사용 |
| 일부 버튼은 손 모양만 보이고 클릭되지 않음 | Native 쪽 hit-map 판독기는 있었지만 C# 게시기가 실제 컨트롤 영역을 싣지 않음 | 프레임과 같은 generation에 WPF Button/CheckBox 실제 사각형을 게시 |
| 바탕화면 아이콘과 겹친 ONHARU 조작부 클릭 불가 | 아이콘 hit-test가 항상 먼저 입력을 가져감 | hit-map 안의 ONHARU 조작부만 ONHARU 입력 우선, 나머지는 아이콘 우선 |
| `선택일 / 이번 주 / 다음 주`를 눌러도 화면이 그대로임 | 내부 상태는 바뀌었지만 고정 캐시 프레임 재게시 누락 | 고정 상태의 일반 Button 처리 후 `SchedulePublish()` 수행 |
| 이동/고정 상태가 직관적이지 않음 | 버튼 문구만으로 현재 상태를 구별하기 어려움 | 버튼 아래 `● 고정됨`(녹색), `● 이동 가능`(주황색) 상태 표시 추가 |
| 종료 로그에 `ObjectDisposedException` | `ExplorerFramePublisher.Dispose()` 뒤 같은 accessor에 `SetActionSink(0)`을 중복 호출 | 중복 호출 제거. Dispose 내부에서 한 번만 해제 |
| Google 로그인 취소가 오류로 기록됨 | 취소를 위해 `HttpListener`를 정지하면 대기 중 예외가 발생 | 명시적 취소 중의 listener 종료 예외를 정상 취소로 분류 |

## 3. 이번 입력 수정의 실제 검증

- 게시된 고정 프레임: 1488×1409.
- hit-map magic 및 frame generation 일치 확인.
- 현재 실측 컨트롤 수 22개(상태에 따라 21~25개).
- 우측 탭 세 개가 실제 hit-map에 포함됨:
  - `선택일`: 대략 `(1186,307)–(1267,339)`
  - `이번 주`: 대략 `(1274,307)–(1354,339)`
  - `다음 주`: 대략 `(1361,307)–(1442,339)`
- 고정 action sink 자동 클릭 결과: 세 탭 모두 메시지 전송 성공, 프레임 generation `376 → 379` 증가. 즉 세 클릭 모두 상태 처리와 재게시까지 완료됨.
- 최종 C# 빌드 성공. 기존 DTO 역직렬화용 필드 경고만 있고 컴파일 오류는 없음.

## 4. 기능 감사 결과

| 영역 | 판정 | 근거/비고 |
|---|---|---|
| 월·주 범위 이동, 오늘 이동 | 구현 확인 | 월 전체 5/6/자동 및 사용자 지정 1~6주 설정과 연동 |
| 선택일, 이번 주, 다음 주 | 자동 입력 검증 통과 | 고정 상태 세 탭 action 및 캐시 generation 증가 확인 |
| 일정 등록·수정·삭제·Todo | 구현 확인 | 고정 raw action과 이동 WPF가 같은 V1 핸들러 사용 |
| 반복 일정 | 자동 검사 통과 | 평일, 선택 요일, 월말 건너뛰기, 마지막 날, 마지막 요일 사례 통과 |
| 알림 | 구현 확인 | 30초 검사, 다시 알림/해제 상태 저장 경로 존재 |
| Google 인증·동기화 | 구현 확인, 외부 조건 존재 | 토큰 분리 저장, 동기화 및 재시도 경로 존재. API 403 rate limit은 외부 일시 오류 |
| 로컬 저장·백업 | 구현 확인 | 계정 분리, 일일 백업, 외부 백업, 설정 백업 경로 존재 |
| 이동·크기 조절 | 사용자 실측 통과 | 위치 조정에서는 V1 WPF 자체 동작 사용 |
| 고정 렌더링·클릭 | 자동 검증 통과 | 캐시 페인트, DPI 환산, hit-map, 아이콘 우선순위 예외 확인 |
| 다중 모니터·해상도 변경 | 코드 경로 확인 | `DisplaySettingsChanged`와 화면 안 복구 처리 존재 |
| 종료 자원 정리 | 결함 수정·빌드 통과 | accessor 중복 접근 제거. 실제 정상 종료 로그 재확인은 후속 실사용 확인 대상 |

## 5. 남은 위험과 확인 항목

1. **실제 마우스 최종 확인**: 자동 클릭은 통과했지만, 사용자가 고정 상태에서 우측 세 탭을 실제 마우스로 한 번씩 눌러 감각과 갱신을 확인해야 한다.
2. **Explorer 재시작 복구**: 복구 코드가 있어도 Explorer 강제 재시작을 포함한 장시간 반복 시험은 별도 회귀 시험으로 남긴다.
3. **hit-map 상한**: 현재 최대 64개이며 실측 21~25개라 충분하다. 향후 화면 조작부가 64개를 넘으면 상한을 확장해야 한다.
4. **Google API 제한**: 403 rate limit은 프로그램 로직 결함으로 단정할 수 없다. 재시도 후에도 반복되면 Google 프로젝트 할당량을 확인한다.
5. **완전 자동 UI 시험 부재**: 핵심 계산과 Native action은 검사했지만 모든 팝업과 모든 마우스 조합을 자동화한 전체 UI 테스트는 아직 없다.

## 6. 결론

이번 점검에서 발견된 고정 상태 우측 탭 입력/갱신 문제와 종료 자원 정리 문제는 수정했다. 현재 코드 조사와 자동 시험에서 새로 확인된 차단급 기능 결함은 없다. 다만 실제 마우스 입력, Explorer 재시작, 다중 모니터 전환은 운영 환경의 수동 회귀 확인 항목으로 유지한다.
