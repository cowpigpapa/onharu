# V1/V2 고정 모드 입력 차이 감사

> 문서 본문의 V3는 현재 공식 ONHARU 2.0의 개발 코드명이다.

작성일: 2026-08-15  
기준: V1 `FamilyPlanner/Step3-Distribution/Source/MainWindow.cs`, V2 `Onharu_v2/App/MainWindow.cs`, `ExplorerFramePublisher.cs`, `ExplorerLayer/DesktopHook.cpp`

## 1. V1 코드로 시작했는데도 차이가 생기는 이유

이동 가능 상태의 V3는 V1과 같은 실제 WPF 창이다. 이 상태에서는 WPF가 마우스 캡처, hover, 클릭, 더블클릭, 휠, 키보드 포커스, 팝업과 부분 다시 그리기를 모두 처리한다.

고정 상태의 V3는 구조가 다르다.

1. WPF 화면을 `RenderTargetBitmap`으로 캡처한다.
2. 32비트 BGRA 프레임을 공유 메모리에 게시한다.
3. Explorer 내부 `SysListView32`의 `NM_CUSTOMDRAW/CDDS_PREPAINT`에서 비트맵을 아이콘 아래에 그린다.
4. Explorer가 받은 입력을 네이티브 훅이 좌표와 action 번호로 변환한다.
5. 숨겨진 WPF 시각 트리에서 해당 좌표의 컨트롤을 다시 찾아 동작시킨다.
6. 결과 화면 전체를 다시 캡처해 Explorer에 게시한다.

따라서 V1 컨트롤 코드가 동일해도 4~6단계에 메시지가 구현되지 않으면 고정 모드에서만 차이가 발생한다. 투명도 슬라이더도 클릭 메시지만 있었고 `버튼을 누른 채 이동` 메시지가 빠져 생긴 사례다.

## 3. 추가 개선 후보

### P1 — 실제 기능 차이

1. **Google 계정 상태 카드 클릭**
   - V1은 `Border.MouseLeftButtonDown`으로 동기화 대기 목록을 연다.
   - V3 고정 hit-test는 Button, CheckBox, Slider, DateTime/PlannerItem Tag만 대상으로 삼는다.
   - 따라서 계정 상태 카드의 빈 부분은 고정 모드에서 반응하지 않을 수 있다.
   - 권장: 카드에 명시적인 action Tag를 부여하거나 Button 형태로 통일한다.

2. **상세 목록 스크롤바 손잡이 드래그**
   - 현재 고정 모드는 휠 스크롤만 지원한다.
   - ScrollBar의 thumb 클릭·드래그, 빈 트랙 클릭(PageUp/PageDown)은 숨겨진 WPF ScrollViewer로 전달되지 않는다.
   - 권장: 휠 사용성이 충분한지 먼저 확인하고, 필요할 때만 스크롤바 전용 hit-test를 추가한다.

3. **투명도 드래그 중 세로로 막대를 벗어난 경우**
   - V1 Slider는 WPF mouse capture로 포인터가 막대를 조금 벗어나도 드래그가 유지된다.
   - V3는 현재 좌표가 Slider 위일 때만 값을 바꾼다.
   - 권장: 실제 사용 중 이탈 문제가 확인되면 네이티브 측에 `opacityDragging` 상태와 capture를 추가한다.

### P2 — 체감 및 표현 차이

4. **hover·눌림·툴팁**
   - 고정 화면은 정적 비트맵이라 WPF의 `IsMouseOver`, `IsPressed`, ToolTip 표시가 자동 동작하지 않는다.
   - 현재는 hit-map 영역에서 손 모양 커서만 제공한다.
   - 기능에는 영향이 없지만 V1보다 상호작용 피드백이 약하다.
   - 권장: 모든 hover를 복제하지 말고, 사용자가 자주 쓰는 헤더 버튼만 필요 시 적용한다.

5. **슬라이더 커서 모양**
   - V1 투명도 Slider는 Arrow 커서다.
   - V3 네이티브 hit-map은 Button/CheckBox/Slider를 모두 손 모양으로 취급한다.
   - 권장: hit-map record에 컨트롤 종류를 기록해 Slider만 Arrow로 분리한다.

6. **키보드 포커스와 접근성**
   - 고정 상태에서는 실제 WPF 창이 숨겨져 Tab, Space, Enter, 방향키로 컨트롤을 조작할 수 없다.
   - 이동 가능 상태와 팝업 창에서는 정상이다.
   - 데스크톱 고정 위젯의 주 사용 방식상 우선순위는 낮지만 V1과 100% 입력 동등성 기준에는 차이다.

### P3 — 구조적 성능 차이

7. **고정 상태 반응 지연**
   - V1은 변경된 WPF 요소만 다시 그린다.
   - V3 고정 모드는 상호작용 뒤 창 전체를 RenderTargetBitmap으로 캡처하고 공유 메모리에 복사한 뒤 Explorer 영역을 다시 그린다.
   - `publishPending`으로 중복 요청은 병합하지만 프레임 전체 게시 비용은 남는다.
   - 선택일/이번 주/다음 주가 이동 상태보다 조금 느린 이유다.
   - 권장: 기능 안정화 후 측정값을 먼저 수집하고, 체감 기준을 넘을 때만 부분 프레임 게시 또는 sidebar-only 캐시를 검토한다.

8. **hit-map 최대 64개**
   - 손 모양 커서용 hit record는 최대 64개다.
   - Google 캘린더와 상세 Todo가 매우 많으면 뒤쪽 컨트롤의 손 모양 표시가 누락될 수 있다.
   - raw 좌표 hit-test는 별도라 클릭 기능 자체가 곧바로 사라지는 것은 아니다.
   - 권장: 실제 64개 초과 사례가 확인되기 전에는 유지한다.

## 4. 팝업과 일정 등록·수정

- `AddItemWindow.cs`, `RecurrenceService.cs`, `RepeatDeleteWindow.cs`는 V1과 파일 단위로 동일하다.
- 설정, 일정 등록·수정, 검색 등은 실제 별도 WPF 창으로 열리므로 열린 뒤의 컨트롤 동작은 V1 방식이다.
- 차이가 날 수 있는 지점은 팝업 내부가 아니라 고정 비트맵에서 팝업을 여는 첫 입력, 팝업을 닫은 뒤 캐시 프레임으로 복귀하는 전환이다.
- 반복 일정 전체 수정 시 원래 시리즈 시작일을 수정 전에 보관하지 않던 V3 회귀는 2026-08-15에 V1 방식으로 복원했다.

## 5. 권장 작업 순서

1. Google 계정 상태 카드의 고정 모드 클릭 보장
2. 투명도 드래그 실제 사용 확인 후 mouse capture 필요 여부 결정
3. 상세 스크롤바 thumb 드래그가 필요한지 사용자 확인
4. 헤더 hover/커서 차이를 디자인 마감 단계에서 정리

현재 기능 안정성을 고려하면 Explorer 페인트 경로나 아이콘 우선 입력 구조는 건드리지 않는 것이 안전하다. 특히 바탕화면 선택 사각형과 아이콘 이동 시 깜빡임이 안정화된 현재 페인트 경로는 유지해야 한다.

## 6. 2026-08-15 반영 결과

- Google 계정 상태 카드에 명시적 고정-mode action Tag를 추가해 카드의 빈 부분을 포함한 전체 클릭을 보장했다.
- 상세 ScrollViewer의 오른쪽 18px 스크롤바 영역을 별도 hit kind로 게시했다. 트랙 클릭과 thumb 형태의 상하 드래그를 고정 모드에서 처리한다.
- 투명도 Slider와 상세 ScrollViewer는 ONHARU 안에서 누르기 시작한 경우에만 네이티브 mouse capture를 사용한다. 포인터가 컨트롤을 조금 벗어나도 드래그가 이어진다.
- 바탕화면 빈 곳에서 시작한 선택 드래그는 capture하지 않으므로 달력 위를 통과해도 기존 Explorer 선택 사각형이 유지된다.
- hit-map 종류를 일반 컨트롤(1), Slider(2), ScrollViewer(3)로 분리했다. Slider와 ScrollViewer에서는 손 모양을 강제하지 않아 V1에 가까운 Arrow 계열 커서를 유지한다.
- hit-map 상한을 64개에서 256개로 확대했다. 실제 게시 확인값은 일반 컨트롤 25개, Slider 1개, ScrollViewer 1개였다.
- 키보드 포커스는 고정 모드에서 강제로 가져오지 않는다. 이를 구현하면 Explorer 아이콘의 방향키·Tab·Enter 조작을 빼앗으므로 데스크톱 본연의 기능을 훼손한다. 키보드 조작은 `위치 조정`으로 실제 WPF 창에 올라온 상태에서 제공한다.
- hover/ToolTip을 비트맵에 매 mouse move마다 다시 게시하는 방식도 적용하지 않는다. 전체 프레임 재게시 증가로 아이콘 이동 끊김과 깜빡임을 되살릴 위험이 더 크다. 대신 컨트롤 종류별 커서 피드백을 유지한다.
- 전체 프레임 게시 구조는 유지한다. 부분 프레임 게시로 바꾸는 것은 Explorer 페인트 안정성에 영향을 주는 별도 아키텍처 변경이므로, 현재 안정된 아이콘/선택 사각형 경로를 보존하는 쪽을 선택했다.

## 7. 2026-08-15 아이콘 이동 깜빡임 보정

- 기존 자동 캡처에서 아이콘을 달력 안으로 이동·드롭하고 다시 밖으로 복귀할 때 229프레임 중 1프레임이 변화 점수 34.701로 검출됐다. 이미지를 확인한 결과 달력이 사라지는 것이 아니라 반투명 프레임이 중복 합성돼 순간적으로 흰색에 가까워지는 현상이었다.
- 원인은 Explorer가 아이콘 드롭 중 하나의 논리적 paint 안에서 중첩 `WM_PAINT`와 여러 `CDDS_PREPAINT`를 발생시키는데, 기존 boolean 중복 방지가 내부 paint 종료 시 바깥 paint 상태까지 해제한다는 점이었다.
- paint 중복 방지를 호출 횟수가 아니라 `paint depth + HDC별 누적 clip region`으로 변경했다. 최외곽 `WM_PAINT`에서만 상태를 만들고 제거하며, 같은 HDC에서는 아직 그리지 않은 영역만 합성한다. 다른 HDC 버퍼가 오면 새 버퍼에는 다시 합성한다.
- `WM_ERASEBKGND`, Explorer 아이콘 hit-test, 바탕화면 선택 사각형 경로는 변경하지 않았다.
- 최종 자동 반복 3회에서 각각 203, 198, 197프레임, 총 598프레임을 검사했다. 세 시험 모두 `frames_over_10=0`, `frames_over_25=0`, worst score 0.0이었다.

## 8. 2026-08-15 섹션 7 결과 정정 및 대체 방식

- 섹션 7의 자동 검사는 아이콘과 떨어진 달력 영역만 측정해 실제 아이콘 둘레의 회귀를 놓쳤다. 실화면에서 달력 소실, 불투명/투명도 급변, 깜빡임이 확인되어 해당 `paint depth + HDC별 region` 변경은 롤백했다.
- 대체 구현은 callback 호출 횟수를 추적하지 않는다. Explorer의 깨끗한 prepaint 배경과 ONHARU 프레임을 메모리 DC에서 단 한 번 합성해 불투명 최종면으로 캐시하고, 모든 prepaint에는 같은 최종면을 `SRCCOPY BitBlt`한다. 같은 픽셀을 여러 번 복사해도 결과가 변하지 않는 멱등 경로다.
- Explorer의 아이콘·hover·selection 그리기 및 hit-test는 그대로 유지하며 `WM_ERASEBKGND`에는 개입하지 않는다. 따라서 바탕화면 선택 사각형의 기존 안정 경로도 유지한다.
- 자동 왕복 검증의 원거리 probe 197프레임은 모두 변화 점수 0.0이었다. 이는 달력 전체 소실과 투명도 급변의 비회귀 근거일 뿐, 아이콘 바로 둘레의 체감 품질은 실화면 검증 대상으로 구분한다.
