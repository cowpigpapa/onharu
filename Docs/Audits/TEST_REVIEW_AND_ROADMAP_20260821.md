# ONHARU 2.1 테스트 정리 및 실행 로드맵

작성일: 2026-08-21  
기준: 사용자 테스트 메모의 중복 항목을 통합하고 실제 2.1 소스와 대조함

## 1. 이번에 즉시 처리한 항목

### 고정 상태 ‘중요한 날’ 버튼

- 원인: Explorer 고정 모드에서 숨겨진 WPF `Popup`만 열어 실제 화면에 나타나지 않았다.
- 수정: 고정 상태에서는 준비된 WPF 화면을 먼저 표시한 뒤 색상 팝업을 열고, 팝업 종료 후 Explorer 고정 레이어로 복귀한다.

### 설정창이 열린 상태의 알림 확인 버튼

- 원인: 설정창의 `ShowDialog()`가 같은 UI 스레드의 다른 창 입력을 막았다.
- 수정: 알림창을 별도 STA UI 스레드에서 표시하고 결과만 메인 Dispatcher로 전달한다. 설정창과 알림창이 서로 입력을 막지 않는다.

### 기념일 등록 후 달력 이동

- 원인: 저장 직후 `selectedDate`와 `shownMonth`를 기념일 날짜로 강제 변경했다.
- 수정: 기념일 등록·수정은 카드 데이터만 갱신하고 현재 달과 선택 날짜를 유지한다.

### 기념일 YYYYMMDD 빠른 입력

- 별도 체크박스 없이 `기념일자` YYYYMMDD 입력칸을 항상 표시하고 오른쪽 달력 아이콘으로도 고를 수 있게 했다.
- 정확히 8자리 날짜만 허용하며 실제 달력 날짜인지 검증한다.
- 예: `19760916`. 1900년 이전 값과 존재하지 않는 날짜는 저장하지 않는다.

### 원하는 달로 이동

- `10년 이전 / 1년 이전 / 1년 이후 / 10년 이후` 버튼과 직접 연도 입력을 함께 제공한다.
- 직접 입력은 Tab, 월 선택, 바깥 클릭 시 적용하며 잘못된 값은 기존 연도로 복원한다.
- 팝업 아이콘을 달력 의미가 명확한 아이콘으로 교체했다.

### 일정 가져오기·내보내기·백업 복원

- 네 개 데이터 작업 버튼은 클릭 시 다른 작업 플래그를 먼저 초기화하여 한 작업만 실행되게 강화했다.
- 백업 복원은 기존처럼 로컬 일정만 읽고, 현재 Google 일정은 메모리에서 따로 보존한 뒤 다시 합친다.
- 복원 완료 시 `로컬 일정만 복원했으며 Google 일정에는 영향이 없다`는 안내를 표시한다.
- 결론: 자동 백업과 일정 내보내기는 모두 로컬 일정 데이터라는 점에서는 같지만 목적이 다르다. 자동 백업은 장애 복구용 세대 보관이고, 일정 내보내기는 사용자가 선택한 파일로 이동·보관하는 기능이다.
- 백업 복원창에 실제 백업 폴더 경로와 `백업 폴더 열기`를 추가하고 목록 안쪽 여백과 스크롤 스타일을 ONHARU 양식으로 정리했다.
- 일정 저장 때마다 당일 계정 백업 파일을 갱신하며, 날짜가 바뀌면 새 날짜 파일을 만든다. 계정별 최근 30개를 보존한다.

### 일정 시간 입력 정리

- `하루 종일`일 때 시·분 선택 영역을 숨긴다.
- `오전` 또는 `오후`를 선택했을 때만 시·분 선택 영역을 표시한다.
- 이월 기능은 기존 데이터 호환 때문에 삭제하지 않고 후속 설정 옵션 대상으로 보류했다.

### 프로 경기 일정

- 메인 헤더에 야구 아이콘과 `준비 중` 안내만 추가했다.
- API·팀 선택·일정 필터는 별도 모듈 설계 전까지 구현하지 않는다.

## 2. 데이터 안전 확인

- `LocalStorage.LocalOnly()`와 `Store.Restore()`는 Google 식별자가 있는 일정을 제외한다.
- 백업 파일 복원 시 현재 Google 일정 목록을 보존하고 로컬 목록만 교체한다.
- 일정 내보내기 JSON도 로컬만 포함한다.
- Excel용 CSV는 사용자가 요구한 전체 일정 보고용이므로 Google과 로컬을 함께 포함한다.
- 따라서 백업 복원·ONHARU 가져오기·내보내기는 Google 서버 자료를 삭제하거나 덮어쓰지 않는다.

## 3. 지금 하지 않고 다음 단계로 분리한 항목

### P0: 다음 안정화 라운드 진행 결과

1. 혼합 DPI 다중 모니터 위치·크기
   - 모니터 장치명과 Win32 물리 픽셀 위치·크기를 추가 저장하고, 시작 시 해당 모니터 작업영역 안으로 복원한다.
   - 연결 해제 시 주 모니터로 안전하게 되돌린다. 실제 100/125/150% 조합 수동 검증은 남았다.
2. 오늘 표시와 선택일 표시
   - 각각 `없음 / 색상 / 테두리 / 색상+테두리`를 제공한다.
   - 두 설정 중 하나가 테두리를 사용하면 다른 쪽은 색상으로 전환하며, 같은 날짜에서는 선택일 테두리를 우선한다.
3. 완전 투명
   - 0%까지 허용하고 트레이에 `투명도 복구 (70%)`를 추가했다.
4. 오른쪽 아래 동기화 상태
   - 기존 상태 문구를 오른쪽 아래의 작은 오버레이로 이동했다.
5. 이월 기능
   - 저장 형식과 기존 일정 호환을 유지하고 설정에서 등록·수정 UI 노출만 제어한다.

### P1: 일기장 모듈

- `App/Diary` 폴더에 일정과 분리된 `DiaryEntry`, 저장소, 편집창, 리더창을 둔다.
- 일기는 기본적으로 로컬 저장하며 Google Calendar 일정과 섞지 않는다.
- 설정: `일기장 사용`, `날짜 더블클릭 동작 = 새 일정 / 일기 쓰기`.
- 헤더: 시간표 옆에 일기장 아이콘.
- 리더 보기: 한 장 보기, 날짜 목록+본문, 월별 타임라인, 검색/즐겨찾기.
- 현재 날짜 더블클릭은 새 일정 기능이므로 설정 없이 즉시 교체하지 않는다.
- 사진 첨부·암호화·클라우드 동기화는 첫 버전 범위에서 제외한다.

### P1: ICS 가져오기·내보내기

- RFC 5545 기반 `.ics` parser/writer를 별도 `App/Interchange` 모듈로 둔다.
- 1차 지원: 제목, 시작·종료, 하루 종일, 설명, UID, RRULE, EXDATE, 알림.
- 가져오기 전에 신규·변경·중복을 미리 보여주며 Google 서버로 자동 업로드하지 않는다.
- 시간대, 반복 예외, 참석자는 손실 가능성을 명확히 표시해야 한다.

### P1: Google 유형 개선

- 현재 Calendar API의 `eventType`은 저장한다: `default`, `birthday`, `focusTime`, `fromGmail`, `outOfOffice`, `workingLocation`.
- 화면에서 유형별 의미와 읽기 전용 제한을 더 명확히 표현하는 작업이 필요하다.
- Google Tasks는 Calendar Events API와 별도 Google Tasks API 및 OAuth scope가 필요하다. OAuth 검증 범위가 바뀌므로 Calendar 개선과 분리한다.
- ONHARU가 현재 Task처럼 인식하는 항목은 Calendar 설명에 Tasks URL이 포함된 일부 항목에 대한 호환 처리일 뿐, Google Tasks 전체 동기화가 아니다.

### P2: 스포츠 일정

- API 이용약관, 호출 제한, 국내 야구·축구 데이터 품질, 팀 ID 안정성을 먼저 조사한다.
- `App/Sports`에 provider 인터페이스, 캐시, 팀 선택, 경기 전용 보기 모드를 분리한다.
- 경기 모드에서는 일반 일정을 삭제하거나 숨김 상태로 저장하지 않고 화면 필터만 전환한다.

### P2: 메일에서 일정 등록

- ONHARU 단독 Windows 앱은 Gmail/Outlook 웹페이지의 우클릭 메뉴를 직접 추가할 수 없다.
- 브라우저 확장 또는 Outlook 추가 기능이 필요하다.
- 1차 현실안은 선택한 텍스트를 등록창에 전달하고 날짜 후보만 채우는 방식이다.
- 완전 자동 의미 추출은 별도 AI 서비스, 개인정보처리방침, 비용 설계 후 검토한다.

### P2: 모바일 앱

- WPF/Explorer 레이어 코드를 Android/iOS로 이식할 수는 없다.
- 공유 가능한 것은 데이터 규격, 반복 규칙, ICS, Google 동기화 규칙이다.
- 권장 구조: Windows 앱 + 모바일 앱(Flutter 또는 .NET MAUI) + 선택적 ONHARU 계정/동기화 API.
- Google 일정은 각 플랫폼에서 Google OAuth로 연결하고, 로컬 일기·설정의 기기 간 동기화는 별도 서버가 필요하다.

### P2: 자동 업데이트·다국어·웹사이트

- 기존 `TODO_NEXT.md`의 GitHub Release manifest와 사용자 승인형 업데이트 방식을 유지한다.
- `onharu.net`에는 소개, 다운로드, 릴리스 노트, 개인정보처리방침, FAQ를 둔다.
- FAQ는 카테고리와 검색을 제공한다.
- Rainlendar 홈페이지처럼 첫 화면 구성을 단순화하되 ONHARU 색상·둥근 카드·정렬 원칙을 유지한다.

## 4. Rainlendar와 비교해 얻은 우선순위

Rainlendar 공식 리소스·릴리스 기록 기준으로 확인되는 강점은 다국어 리소스, 스킨, 이벤트·Task·알림, iCalendar, 인쇄, 여러 온라인 캘린더, 모니터 연결/해제 위치 처리다.

ONHARU의 차별점:

- Windows 아이콘 아래에 실제로 합성되는 큰 월간 달력.
- Google 일정과 로컬 일정을 한 화면에서 구분해 사용.
- 한국 사용자 중심의 음력·24절기·대한민국 휴일.
- D-Day·기념일·시간표·세밀한 주 범위와 표시 옵션.
- 일정 가져오기 전에 신규·변경 후보를 확인하는 안전한 로컬 데이터 흐름.

Rainlendar에서 우선 참고할 항목:

1. 혼합 모니터 연결·해제 위치 복구.
2. ICS 호환성과 반복 Task 인쇄.
3. 다국어 리소스 패키지 구조.
4. 자동 업데이트와 변경 내역 안내.
5. 단순한 제품 홈페이지와 검색 가능한 FAQ.

참고:

- https://github.com/rainlendar/Rainlendar-Resources
- https://github.com/rainlendar/Rainlendar-Resources/releases
- https://developers.google.com/workspace/calendar/api/guides/event-types

## 5. 코드 감사에서 추가로 확인한 개선점

- `SettingsWindow.cs`와 `AddItemWindow.cs`는 UI 생성 코드가 각각 매우 크다. 기능 추가 전에 섹션별 빌더 partial/helper 분리가 필요하다.
- 네이티브·DWM 경계의 빈 `catch`는 앱 생존 목적이지만 최소 진단 코드가 없어 장애 원인을 숨길 수 있다. 사용자 정보 없이 오류 코드만 기록하는 방식이 필요하다.
- Google `eventType`은 저장하지만 표시 정책이 없어 읽기 전용 특수 이벤트가 일반 일정처럼 보일 수 있다.
- 설정의 데이터 작업은 bool 여러 개보다 단일 enum/action 값이 장기적으로 안전하다. 이번에는 상호 초기화로 오동작을 막았고 다음 리팩토링에서 enum으로 교체한다.
- 다중 모니터 문제는 `FitWindowToScreens` 단위검사만으로 부족하다. 100%/125%/150% 조합과 좌우·상하 배치 수동 시나리오가 필요하다.

## 6. 검증 결과

- C# 빌드 성공.

- 2026-08-22 사용자 실기기 PASS: 필터 변경 시 투명도 유지, 안전한 백업 복원 확인 단계, 새 일정·수정 무스크롤, 입력 중앙 정렬, D-Day·기념일 당일 강조, 고정 상태 주요 입력, 하단 동기화 상태.
- 남은 환경 의존 수동 확인: 100/125/150% 혼합 DPI 모니터 이동·고정·재실행.
